# 实现计划索引

设计文档：[`../specs/2026-09-24-agent-lens-design.md`](../specs/2026-09-24-agent-lens-design.md)

每个阶段拆成 3 到 4 份**独立可执行**的计划。每份计划自带测试循环与验收标准，单独执行就能产出一个可验证的成果，不需要等其他计划完成。执行顺序按编号，但相邻计划之间只通过「Interfaces」小节声明的接口耦合。

## 阶段 1 · 端到端最小闭环

| 计划 | 目标 | 产出 | 依赖 |
|---|---|---|---|
| [P1.1](2026-09-25-p1-1-codex-log-parser.md) | 把 Codex 的 JSONL 解析成结构化对象 | `models.py` / `parser.py`，纯函数，零 IO | 无 |
| [P1.2](2026-09-27-p1-2-storage-layer.md) | 存储层：SQLite schema、幂等写入、水位表、成本计算 | `storage.py` / `schema.sql` / `pricing.py` | P1.1 的模型 |
| [P1.3](2026-09-28-p1-3-collector.md) | 采集守护进程：扫描、增量读、脱敏、队列、Langfuse 上报 | `collector.py` / `redact.py` / `reporter.py` | P1.2 的存储接口 |
| [P1.4a](2026-09-28-p1-4a-query-api.md) | 查询 API：聚合查询、设置写接口、静态托管 | `queries.py` / `api/` | P1.2 的查询接口 |
| [P1.4b](2026-09-28-p1-4b-web-frontend.md) | Web 前端五页：总览、项目、会话、工具、设置 | `web/` | P1.4a 的接口契约 |

**说明**：P1.4 已按上述建议拆成 P1.4a（FastAPI 查询接口）与 P1.4b（Vue 前端）。两者的接口边界固定在 P1.4a 的「前端契约」一节，P1.4b 的 `types.ts` 必须与该节逐字对齐。

**前端设计**：P1.4b 开头有「深空控制台」设计方向（令牌、排版、动效、Element Plus 覆盖策略），三个愿望词是**简约、科技感、交互丝滑**。

**阶段 1 完成标志**：`uv run agent-lens collect` 常驻采集真实数据，网页上能看到总览、项目、会话、工具调用四个页面，设置页能改价目表，Langfuse 上能看到按 turn 组织的 trace。

## 阶段 2 · 分析深化

| 计划 | 目标 | 依赖 |
|---|---|---|
| P2.1 | 上下文成本分解器：把 input 拆成固定指令 / skill 目录 / 历史对话 / 工具输出 | P1.1 的模型 |

**阶段 2 的计划在阶段 1 完成后编写**。原因：P2.1 依赖设计文档第 13 节的待验证问题 1（时间戳粒度）与问题 2（reasoning token 计价）的结论，现在写会写出错误的分母。

## 阶段 3 · 传输效率与数据生命周期

| 计划 | 目标 | 依赖 |
|---|---|---|
| P3.1 | OTLP 接收器（或接入 Langfuse OTLP 端点），落地 TTFT / TBT | 待验证问题 3 的结论 |
| P3.2 | 传输效率前端页：延迟分布、cache 趋势、上下文膨胀曲线 | P3.1 |
| P3.3 | 归档与保留策略：压缩、水位校验、只归档不删除的默认行为 | P1.3 的采集器 |

**阶段 3 的计划在阶段 2 完成后编写**，其中 P3.1 的形态取决于 Langfuse 的 OTLP 端口是否接收 metrics——若不接收，就需要自建接收器，计划内容差别很大。

## 每份计划的执行约定

- 严格按任务顺序执行，每个任务自带「写失败测试 → 跑测试确认失败 → 写最小实现 → 跑测试确认通过 → 提交」五步。
- 任务之间的接口在每份计划的「Interfaces」小节声明。改动接口要同步更新下游计划。
- 任何任务里如果发现设计文档的假设与真实数据不符，**停下来更新设计文档**，不要就地绕过。
- 不要在计划外顺手重构。发现的问题记到 issue 或文档里，单独排期。

### P3.4 说明（2026-09-29 记录，2026-09-30 完成）

**计划**：`docs/superpowers/plans/2026-09-30-p3-4-project-attribution.md`（三个任务全部完成）。

**原状（2026-09-29）**：`storage.resolve_project()` 只看 `project_paths` 这张手动映射表；没有配置映射时，
所有会话都落到「未归类」。真实库实测：当时 5 个会话全部是「未归类」，`project_paths` 映射 0 条。

**落地后的三条裁决**（细节见计划文档）：

- **只认磁盘上真实存在的路径**：日志里的陈旧 `cwd`（目录已改名/搬走）不做 basename 兜底，留在「未归类」，
  交给设置页手动映射。实测吃亏面：2026-09-30 的 12 个会话里有 6 个是这种陈旧路径。
- **向上查到用户主目录就停**，主目录本身不算仓库根：`~/.git` 不该吞掉 `~/projects` 这类元目录。
- **项目名 = 仓库根目录名**：同名仓库会合并成一个项目名，已知限制，不加去重后缀。

**验收方式**：真实库重算后 `/api/projects` 零配置下返回多于 0 个项目，且会话总数不变。

**仍未覆盖**：Windows 分隔符与大小写归一化、同一目录下多个 git 仓库的取舍——当前采集器跑在
POSIX 容器里，先不做。

**阶段 3 的计划在阶段 2 完成后编写**，其中 P3.1 的形态取决于 Langfuse 的 OTLP 端口是否接收 metrics——若不接收，就需要自建接收器，计划内容差别很大。

## 每份计划的执行约定

- 严格按任务顺序执行，每个任务自带「写失败测试 → 跑测试确认失败 → 写最小实现 → 跑测试确认通过 → 提交」五步。
- 任务之间的接口在每份计划的「Interfaces」小节声明。改动接口要同步更新下游计划。
- 任何任务里如果发现设计文档的假设与真实数据不符，**停下来更新设计文档**，不要就地绕过。
- 不要在计划外顺手重构。发现的问题记到 issue 或文档里，单独排期。

# 面试素材：这个项目要讲的故事

这份文档不是项目介绍，是**讲故事用的素材库**。每个故事的结构固定：一句话结论、背景、我做了什么、
支撑结论的真实数字、以及被追问时怎么答。

用法：面试前过一遍，挑 3 到 4 个讲。数字全部来自本仓库的真实运行记录（测试输出、真实会话重放、
`.superpowers/sdd/` 下的 ledger），不是估算。

**一条自我要求**：每个故事都要能说出「我一开始想错了什么」。讲不清自己错在哪的故事，听起来都像
念功能列表。

---

## 故事 1 · 一个技术判断：为什么把 Langfuse 定位成「可重建的视图」

**一句话**：当上游的保留期不由我控制时，我把上游降级成视图，而不是数据源。

Langfuse 免费版保留 30 天。常规做法是把它当数据库用——反正 trace 都在上面。但那样一来，30 天前的
数据就永久消失了，而我的分析需要按项目看长期趋势。

所以我定了三层：**原始 JSONL 是事实源（Codex 写的，永久保留），SQLite 是投影，Langfuse 是可重建的
视图**。任何一层都能从上一层重放出来。

这个判断落地成了三个具体的约束：

1. 采集器先写库，再单独入队上报——Langfuse 挂了不影响本地分析（`report_queue` 落盘，重启自动重投）。
2. 幂等键是 `(文件路径, ordinal)`，所以采集器可以随时全量重跑而不产生重复数据。
3. 成本**不落库**，只在查询时用价目表算——改价后历史趋势一致重算，不会出现断层。

**数字**：全量重放真实会话两次，写入行数完全一致；真实库累计 1100 次调用、1.45 亿 input token。

**被追问「那 Langfuse 还有什么用」**：省掉外围苦工——上报、存储、通用展示、分享链接、标注。
凡是它能做的我都不做，只有它做不到的才自研。

## 故事 2 · 一个踩坑过程：`thread_token_usage` 跨文件重置

**一句话**：我用一个校验公式发现总量算错了，追下去发现是「会话级累计字段会在文件边界重置」。

Codex 的每条 token 记录里有三个字段：`usage`（单次调用）、`turn_token_usage`（本轮累计）、
`thread_token_usage`（本会话累计）。最直觉的做法是读最后一条记录的 `thread_token_usage` 当会话总量——
省事，不用求和。

我一开始就是这么做的，直到写了一条自检：**`Σ usage.input_tokens` 应该等于各文件内最后一个
`thread_token_usage.input_tokens` 之和**。

**数字**：会话 `01a0c8ec` 横跨两个文件，文件一的累计停在 4,209,407，文件二却从 21,052 重新开始。
按公式算：`4,209,407 + 90,729 = 4,300,136`，正好等于 `Σ usage`。这个公式在全部会话上成立，
而「直接读最后一个累计值」会少算 90,729。

修正成两条硬性规则，写进设计文档并落到代码：**所有总量统计一律对 `usage` 求和，绝不读累计字段**；
累计字段只用于自检。

**被追问「怎么保证以后不再犯」**：这条自检成了测试策略的第 1 条，用真实数据的裁剪样本做 fixture，
核心断言就是这个公式。

## 故事 3 · 一个差异化能力：把工具调用失败折算成 token 成本

**一句话**：工具失败会触发重试，而重试那次调用的 input 是几万到十几万 token——没人把这两件事连起来算过。

Langfuse 能告诉你「这个 span 失败了」，也能告诉你「这个模型花了多少钱」，但它不会把两者相乘。
而在 agent 场景里，一次失败的 `exec_command` 不是零成本的：模型会看到报错、重新推理、再调一次，
每一次重试都要把整个上下文重新发一遍。

**数字**：实测单次调用的 input 在 18,974 到 106,262 token 之间。所以我定义了一个派生指标
**失败成本 = 该 turn 内因工具失败而产生的额外 api_call 的 input token × 对应单价**，并在工具页
与总览页一起呈现。

实现上它不落库，是查询时算的——因为它依赖「哪些调用是重试」这个判定，而判定规则我可能还要改。

**被追问「怎么判定哪次是重试」**：按同一会话内、工具失败之后的调用算重试，用 `(session_id, file_path)`
定界。这个口径是近似的（同一轮里模型也可能因为别的原因再调一次），所以我把它标成派生指标而不是事实，
口径要改随时改。

## 故事 4 · 一个工程判断：从「我本机能跑」到「别人能访问」

**一句话**：把一个只在本机跑的工具，变成一台常驻小服务器上别人能访问的服务。

这一层跨过的东西是：内网寻址（为什么同一个局域网里不用记 IP）、监听地址的语义
（`127.0.0.1` / `0.0.0.0` / 具体网卡分别对谁敞开）、开发模式与生产模式的差别、反向代理的职责、
暴露面的三档（内网 → 覆盖网络 → 公网入口）、进程常驻与自启、以及「数据不能跨机器共享」。

**关键判断**：为什么「端口转发 + DDNS」是最差的一档——因为这个服务**没有鉴权**，
而它的日志接口会返回会话的元数据。把它直接暴露到公网，等于把工作内容交出去。

所以我选的是覆盖网络（Tailscale）：不开放任何公网端口，访问范围由身份决定。

**被追问「SQLite 为什么不能放共享盘」**：WAL 依赖文件锁，SMB / NFS 上的锁语义不保证，
多写者会直接损坏库。结论是「写入者必须与库同机」，跨机器只做只读副本（先 checkpoint 再 rsync）。

## 故事 5 · 阶段 2 新增：上下文分解的「分母」是怎么校准的

**一句话**：我本来打算用「字符数 ÷ 3.5」估 token，真实数据告诉我这个估算系统性偏低 17% 到 26%，
于是我改成锚定真实 `input_tokens`，并把差额单列成一块。

目标是回答「这些 token 花在什么地方」。数据库里没有正文（设计原则：正文不入库，只存长度和
「文件 + 行号」指针），所以分解只能回到原始 JSONL 重放。

重放时先踩到一个顺序问题：`token_usage_record` 在文件里的位置是「本次调用的产出之后、工具输出之前」，
所以「把本次产出也算进本次 input」是错的。正确做法是模型产出先进 buffer，遇到工具输出才提交进上下文，
快照取的是**未含 buffer 的已提交内容**。

然后才是分母问题。我用官方给的换算比率（中文 0.6 token/字符、其他 0.3）做纯字符估算，拿真实数据一对：

**数字**：918 次调用，`真实 input ÷ 字符估算` 的中位数是 **1.206**，p10 是 1.008、p90 是 1.574。
余额来自每次调用都固定重发的工具定义与请求框架。

所以我加了两件事：**用真实 `input_tokens` 做锚**（四块按估算值占比摊派），**把余量单列成第五块
「未归因」**，保证五块之和恒等于真实分母。跑真实库的结果：工具输出 36.1%、历史对话 31.9%、
未归因 26.1%、固定指令 3.2%、skill 目录 2.8%。

**被追问「26% 未归因是不是说明你这套不准」**：它恰恰说明**不锚定真实值会更不准**。字符估算能解释
74% 的 input，剩下的是我拿不到结构的请求框架开销。我选择把它诚实地单列出来，而不是按比例摊进四块——
摊进去会让四块的数字好看，但那是假的。

## 故事 6 · 阶段 2 新增：一个数据推翻直觉的发现

**一句话**：同一模型的「低推理强度」平均单次成本反而更高，因为 cache 命中率差了 23 个百分点。

我做了按 `(模型, 推理强度)` 的成本对比，本来预期是「强度越高越贵、贵模型更贵」。真实数据里出现了一行
不符合直觉的：

**数字**：

| 模型 / 强度 | 调用次数 | cache 命中率 | 平均成本/次 |
|---|---|---|---|
| deepseek-flash / high | 983 | 99.5% | $0.001392 |
| deepseek-v4-pro / high | 10 | 90.2% | $0.001996 |
| deepseek-v4-pro / low | 3 | 66.9% | **$0.003076** |

`v4-pro` 的 low 比 high 贵了 54%，原因不是单价，是那 3 次调用的 cache 命中率只有 66.9%。

结论直接改了产品设计：**这一页必须把 cache 命中率与成本并排显示**，只比单价会得出错误结论。

**被追问「3 次调用能说明什么」**：不能说明统计规律，只能说明这个页面**必须**把命中率和成本放在一起，
否则用户会误读。我把这个当成界面设计的证据，不当成成本结论——样本量我在页面上也标注了。

## 顺带能讲的两个小故事

**一个前端 bug 的定位（KI-1）**：点左侧导航后内容区空白，只有刷新能恢复，控制台一句报错都没有。
根因是 `<Transition>` 只能包裹单个根节点，而六个视图都是多根片段，`mode="out-in"` 下过渡拿不到
要进入的元素，新视图根本没挂载。修法是给过渡补一层按路由 key 的单根容器。

我把它做成了回归探针（`scripts/nav-smoke.mjs`，CDP 直连 Chrome）：修复后 8 步全过；把代码退回修复前，
同一个探针**必须失败**——`main.content` 子元素从 3 变 0，`innerHTML` 只剩 `<!---->`，与原报告逐字吻合。
**反向对照存在的意义**是证明探针不是「永远通过」。

**一个凭据泄露的真实事故**：开发期间我检查 `~/.git-credentials` 时把 token 打印进了会话，
而这个项目的采集对象正是这些会话日志。所以脱敏不是「有空再加」的功能，是**写库之前**的强制处理，
规则覆盖 `ghp_` / `github_pat_` / `sk-` / `AKIA` / JWT / Bearer / `password=` 等形态，
且原始文件永不被修改。这个故事的价值在于：它是我自己踩的，不是抄来的。

## 诚实的边界（准备好被追问）

- **单用户、无鉴权**。它不是产品，是自用工具；「暴露面三档」的设计是加分项，别把没鉴权说成优点。
- **token 估算有误差**（未归因约 26%）。主动说出来，比等面试官发现好。
- **明确不做**：重复劳动检测（相似失败聚类、同一文件反复读）、多 agent 协作分析、预算告警。
  列为非目标比硬做半成品好。
- **项目归属的三级规则里，自动推断有明确的盲区**：日志里的 `cwd` 指向已改名/搬走的目录时不做兜底，
  元目录（`~/projects` 这种下面开多个仓库的目录）也判不出来，两者都留在「未归类」交给手动映射。
  实测 12 个会话里 6 个属于这类，所以「项目视图」的内容量取决于你有没有把工作目录整理进白名单。
  规则与裁决见 `docs/superpowers/plans/2026-09-30-p3-4-project-attribution.md`。
- **一次方法论上的让步**：阶段 2 的 12 个任务原本按 subagent-driven development 派发，
  但派发通道连续两次投递失败（子代理 12 分钟无响应、无产物），按仓库约定改由我一人实现。
  代价是**少了独立评审席位**。如果你要拿「做过 subagent 协作」当卖点，这条必须如实说。

# 实现计划索引

设计文档：[`../specs/2026-09-24-agent-lens-design.md`](../specs/2026-09-24-agent-lens-design.md)

每个阶段拆成 3 到 4 份**独立可执行**的计划。每份计划自带测试循环与验收标准，单独执行就能产出一个可验证的成果，不需要等其他计划完成。执行顺序按编号，但相邻计划之间只通过「Interfaces」小节声明的接口耦合。

### P3.4 待办说明（2026-09-29 记录，未开工）

**现状**：`storage.resolve_project()` 只看 `project_paths` 这张手动映射表；没有配置映射时，
所有会话都落到「未归类」。真实库实测：5 个会话全部是「未归类」，`project_paths` 映射 0 条。

**缺的是什么**：设计文档 9.2 承诺了三级归属——手动映射 > **从 `cwd` 向上查找 `.git` 目录作为仓库根**
> 未归类兜底。中间那一级从未实现（全仓库搜 `.git` 推断逻辑，零命中），所以「项目视图」这一页在
没有手动配置时基本没内容。

**为什么放到阶段 3 而不是现在补**：它不是一行代码。要处理的是——向上查找的边界（查到 `/` 还是查到
用户主目录就停）、同一个工作目录下多个 git 仓库、`D:\codex\wzy_workstudio` 这类「元目录」下开多个项目的
情况、以及路径大小写与 Windows 分隔符归一化。这些都会影响已有数据的归属，需要一次重算
（`refresh_session_projects` 已经具备重算能力，但缺的是自动推断的数据源）。
现在插进阶段 2 会把「分析深化」这条线打断。

**验收方式（开工时按这个写计划）**：给定一批真实 `cwd`，自动归属结果与手动核对的期望一致；
`/api/projects` 在零配置下返回多于 0 个项目；重算后会话数不丢。

**阶段 3 的计划在阶段 2 完成后编写**，其中 P3.1 的形态取决于 Langfuse 的 OTLP 端口是否接收 metrics——若不接收，就需要自建接收器，计划内容差别很大。

## 每份计划的执行约定

- 严格按任务顺序执行，每个任务自带「写失败测试 → 跑测试确认失败 → 写最小实现 → 跑测试确认通过 → 提交」五步。
- 任务之间的接口在每份计划的「Interfaces」小节声明。改动接口要同步更新下游计划。
- 任何任务里如果发现设计文档的假设与真实数据不符，**停下来更新设计文档**，不要就地绕过。
- 不要在计划外顺手重构。发现的问题记到 issue 或文档里，单独排期。
